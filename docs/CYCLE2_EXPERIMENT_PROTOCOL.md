## Hypotheses and bounded comparisons

**H1, primary:** role-qualified evidence prevents wrong-object and whole-versus-component mistakes better than the frozen system and a simple category/type guard, without unsupported hard exclusion or a material official-score regression. Use one signature implementation, not a broad search over classifier thresholds.

**H2, optional supporting probe:** complete query-relevant source spans under the same 256-token pair limit improve fixed-query ranking beyond ordinary head truncation and a generic lexical-window control. The majority of old misses never enter the reranker prefix, so do not claim this can solve every miss. At most one protected-packing variant; no new model or training.

**H3, optional reliability probe:** a single bounded optional-model worker can return a legal sparse result after a real stalled/failed worker without discarding corrected intent. Only implement if the proof can justify healthy-run overhead. Process isolation is ordinary engineering, not the novelty claim.

Initial comparisons hold the existing model/revision, four CPU threads, 120 retained candidates, at most 30 reranker pairs, 256 tokens per pair, blend weight 0.75, fixed Top 10 and existing `other` question policy constant. H1's targeted simple control uses ordinary category/title type matching without role scope. It receives no label or sample-specific rules. H2's lexical control gets identical raw fields and token/pair budgets. Do not conflate changed input packing with a larger model.

Allow at most three new primary configuration runs during development: role evidence, protected packing, and their combination only if each earns a separate reason to remain. Baselines and matched simple controls do not count as novel configurations, but every run is retained. Repeated bug-fix runs are explicitly marked debugging/development; they are not independent experiments. Do not run a Cartesian product or add parameters after validation.

## Promotion and rejection gates

All gates apply before opening validation outcomes:

- Correctness first: no newly known unsupported hard exclusions, fabricated catalog facts, invalid IDs, stale-correction regressions or label access. An unknown/ambiguous role must remain eligible. A missing check is unverified, never a pass.
- H1 capability gate: at least 20 percentage points improvement in case pass rate over the frozen baseline and at least 10 points over the simple guard on the role/scope diagnostic subset, with zero new false-hard-exclusion assertions. Small counts make this a practical gate, not a significance test. If the simple guard matches, retain the simpler behavior and reject the signature claim.
- Official public regression floor: no more than 0.01 absolute TechnicalScore loss and 0.02 absolute HitRate loss against frozen Mercury on the same 200 development sessions. Better constraint fidelity does not justify claiming a score gain when score declines.
- General ranking improvement is claimed only for a measured gain of at least 0.01 on the relevant same-set score comparison with paired uncertainty disclosed. H1 may earn a narrow semantic-reliability benefit without earning this broader claim.
- H2 must outperform generic lexical packing at equal budgets on a fixed-query comparison and not violate the public regression floor; otherwise leave it disabled. Better text appearance alone is insufficient.
- Local healthy-run engineering limits: warm p95 below 1.0 second and no more than twice the matched frozen run; total process peak RSS below 2 GiB; required assets remain below 0.5 GiB. These are local selection caps, not organizer-approved limits. Measure child+parent separately if using process isolation; do not omit child memory.
- Optional worker fault path: a declared per-request timeout plus at most one second cleanup tolerance; no surviving worker after `close`; no stale response accepted for another request. Cold-start timeout is separate. State remains parent-owned. If actual input-token usage is unavailable on a fault, disclose that limitation rather than inventing exact counts.

Choose at most one enhanced candidate and the frozen fallback before validation. Freeze all runtime, adapter, evaluator, tests and configuration hashes. Run frozen baseline, the predeclared simple guard, and the selected enhanced candidate once each on locked validation; controls are fixed comparators, not additional tunable contenders. Record a consumed-validation ledger. No implementation or configuration retuning from its outcomes may retain the “held-out” label.

If validation does not meet the relevant practical gate, select the frozen fallback or the demonstrably simpler control, preserve the unsuccessful mechanism as a disabled experiment, and state the negative result. A post-validation correctness fix consumes that validation for the changed source; subsequent results become development evidence and require a new independently locked test for further generalization claims.

## Metrics and reproducibility

Record all official metrics, n and per-scenario counts; paired per-session score deltas with a 95% bootstrap interval, 10,000 resamples, seed 20260826. Intervals are exploratory and not multiple-testing adjusted. Report capability pass counts both by case and assertion, per group, with failures and unverified checks. Group role/scope assertions before looking at results; do not choose the successful groups afterwards.

For fixed-query component checks, store the visible query, exact shared candidate IDs and source hashes independently of question policy. Keep target joins in evaluator-only code. Report candidate/prefix recall separately from final ranking and end-to-end dialogue metrics. An ever-retrieved target does not prove every turn's retrieval was adequate.

Runs use fresh names, exact source snapshots, data/config hashes, wall time, cold start, p50/p95/max latency, memory, actual token counts and fallback/error counts. Run heavy experiments sequentially. Preserve the unmodified catalog/evaluator hashes. Actual offline and missing/corrupt model checks supplement mocked unit failures. No paid APIs, hosted inference, source uploads to external analysis services or new model downloads are planned. Authorized private GitHub checkpoints exclude datasets, model assets and local evaluation traces.

## Demo selection and interpretation

Select the first real-catalog development conversation, in a predeclared stable order, where the new mechanism improves a source-verifiable wrong-role decision over both controls. If none exists, do not invent a demonstration: show the negative experiment and the strongest honest baseline behavior. Include a reverse intent/correction and an ambiguous or missing-evidence case. Clearly distinguish a reproduced model intervention from a factual catalog quote and from any real-world causal claim.

The final artifact reports what improved, what did not, and the largest remaining threat to validity. Neither these tests nor the old public score forecast first place, private-test performance or real shopper conversion.

# Cycle 3 score-improvement campaign

Registered 27 August 2026 before a Cycle 3 target pack, any Cycle 3 score-bearing run, or a new ranking mechanism. The objective is to find a reproducible, legitimate route from the selected public TechnicalScore of `0.786724` toward `0.80`. A score of `0.99` remains an aspiration, not a forecast or a selection criterion: the unchanged intent-change gate gives the released public set a target-knowing upper bound of `0.992200`, and no legal runtime has target access.

## Starting point and data boundary

The control is the current `configs/selected.json`: sparse retrieval, 120 retained candidates, rerank of at most 30 pairs at 256 tokens per pair, reranker blend weight `0.75`, existing state and question policy, and grouped alternatives. It previously scored `0.786724` on all 200 released sessions. Those 200 sessions are development data only. Both 32-session Cycle 2 target splits and the Cycle 2 capability sets are also consumed; they must not be reopened as held-out evidence for this campaign.

## Hypotheses and matched controls

The campaign begins with the error source most plausibly able to recover the three or four strong sessions needed for `0.80`: a relevant item can enter the 120-candidate pool yet never reach the 30-item reranker prefix. Every score-bearing arm keeps the catalog, evaluator, model revision, 120-candidate ceiling, 30 reranked pairs, 256-token pair ceiling, blend weight, Top 10 output ceiling, and question policy fixed.

### A. Constraint-covering candidate admission

Before neural reranking, choose the existing 30-item prefix from the same 120 retrieved candidates. The candidate must preserve high sparse-route leaders while admitting a small, deterministic set that covers active, source-supported hard or rare preferences. It may not use target IDs, sample IDs, future turns, result labels, hand-written product rules, or fabricated facts.

Compare exactly these modes before any combination:

1. `prefix`: the present first-30 behavior.
2. `stratified`: a simple rank-spread control that has no preference coverage logic.
3. `cover`: evidence-supported preference coverage with deterministic tie-breaking.

Record candidate-pool recall, reranker-prefix recall, final rank, and route composition per scenario in evaluator-owned artifacts. A target appearing somewhere in 120 is not evidence that the prefix is adequate.

### B. Factored fielded retrieval

Run this only if A does not earn the screening gate or its diagnostics show that misses are absent from the 120-candidate pool. Compare the existing broad sparse query with one fixed field-aware retrieval plan using catalog category/object terms and only reliable active requirements. The matched control is a naive fixed-budget union of the same routes. Each arm still returns exactly the same maximum 120 candidates to the downstream pipeline. No query expansion model, learned weights, sample-specific branches, or larger candidate pool is allowed.

### C. Protected evidence serialization

Run this only if a surviving A or B arm shows sufficient prefix recall but weak final ordering. Within the existing 256-token pair budget, preserve the title, category, and source-backed spans relevant to active positive and negative preferences. Compare it with the present field-head serializer and one ordinary lexical-window control at identical pair and token budgets. It may not infer unrecorded material, fit, compatibility, or attribute values.

### D. Role and component semantics

This is a capability and demonstration track, not the first score route. Before implementing it, lock independently authored mini-catalog capability cases covering whole-product versus component evidence, negative evidence, ambiguity, and correction. It can be promoted only if it prevents an unsupported hard exclusion and passes its predeclared cases. It does not earn a broad score claim merely by sounding more precise.

The following are registered as rejected starting points: a generic dense or hybrid retry, reranking 60 candidates, generic evidence-length expansion, adaptive question-policy sweeps, label reconstruction, target lookup, or any oracle-like logic. Their prior evidence or resource cost does not justify another unbounded search.

## Execution order and gates

1. **Lock:** create the target pack and provenance snapshot; verify the lock read-only. Author and lock capability cases before their source changes. No score results are opened in this phase.
2. **C0 parity:** run the unchanged selected configuration once on screening to establish a same-pack control. Record all official metrics, scenario counts, candidate/prefix recall, run hashes, p50/p95/max latency, prompt-token count, errors, and fallbacks.
3. **Screening:** implement and test one registered arm at a time. Each configuration/source hash receives a new named output directory; failed runs remain recorded. A mechanism earns confirmation only with at least `+0.010` TechnicalScore versus C0 on screening, no more than `-0.010` HitRate overall, no scenario score loss worse than `0.020`, valid IDs only, and no material resource breach. For A or B, its diagnosed candidate or prefix recall must improve as well; a ranking gain with no retrieval explanation does not earn a causal claim.
4. **Confirmation:** freeze C0, one matched simple control, and at most one screening survivor. Verify source/config/model/input hashes, then run each configuration exactly once on confirmation. Promotion requires non-negative overall score delta, no more than `-0.010` HitRate, and no correctness or resource failure. The confirmation result is consumed regardless of success.
5. **Validation:** freeze the finalist, the selected control, runtime, tests, configurations, and hashes before opening validation. Run each once. No repair or retuning can retain the word “held-out”; a changed source requires a new lock.

The public 200-session score may be run only as a descriptive regression check after a mechanism has passed fresh screening. It is never used to choose a variant after confirmation or validation and does not turn public data back into a holdout.

## Resource, correctness, and reporting rules

The local feasibility caps are warm p95 under 1.0 second and no more than twice C0's matched runtime, with no increase in model size, network access, paid service, external source upload, or undisclosed background process. Treat a missing measurement as unverified, not a pass.

All final reporting will show the official score components, `n`, scenario distribution, candidate/prefix recall, paired per-session deltas with an exploratory 10,000-resample bootstrap interval (seed `20260826`), resource measurements, failed arms, and the exact validation-consumption ledger. It will distinguish observed public behavior from any claim about the organizer's private evaluation. An honest negative result preserves the selected baseline; it does not get rewritten into a claim of progress.

Private GitHub checkpoints may include source, tests, configurations, protocols, and aggregate receipts. They must exclude target packs, capability validation content, raw traces, catalog data, model assets, and `submission/README.md`, which remains empty until project completion.
